## Features and effects

### F1: Claim a unique session label

- Problem and current behavior: agents register native addresses such as `codex:SESSION`; humans and agents must copy those addresses.
- Proposed behavior: `llm-bus whoami --label builder` claims `builder` for the invoking main session. `whoami`, `list`, and `agents` show label and exact address. Repeating the same claim succeeds. Another live session claiming `BUILDER` fails atomically.
- Effect on the code: the mailbox owns label claims alongside native session lifecycle; CLI registration accepts an explicit optional label.
- Scope and compatibility: uniqueness covers a repository and linked worktrees across Claude/Codex on one machine. Different machines own independent namespaces; qualify remote labels with machine/repository. Exact addresses remain valid. One session has at most one current label in its current scope. An explicit new label atomically replaces its previous claim; failed replacement preserves the old claim. Ordinary registration never silently changes a claim.
- Acceptance outcomes: concurrent claims produce one winner; failed claims change neither claimant identity nor prior label. Existing mail, locks and grants remain keyed to exact addresses.
- Execution mapping: Tasks 1 and 3.

### F2: Resolve labels everywhere an agent address is accepted

- Proposed behavior: `send builder`, `history --peer builder`, and coordination owner commands accepting `--coordinator` or `--recipient` resolve a current label to one exact identity. `send machine/repository/builder` resolves an eligible remote roster label.
- Scope and compatibility: project labels, lock resource names, message IDs, report codes, GitHub users and collaboration contexts retain their own meanings. Commands without address inputs require no new label parameter. Labels never replace native sender identity detection.
- Acceptance outcomes: every existing address input supports labels; authorization, reply checks, persisted participants, enrollment and assignment continue using the resolved exact identity. Reusing a label never transfers history or authority.
- Execution mapping: Tasks 2 and 3.

### F3: Release on session close

- Proposed behavior: the existing `SessionEnd` hook ends only its native session and removes that session's claim in the same transaction. Duplicate or delayed close events cannot remove a different session's reused label. The existing 24-hour inactivity expiry also releases claims. A resumed expired/ended session must explicitly reclaim its label.
- Scope and compatibility: turn completion does not release a label. Hooks remain main-agent-only. Missing host close events are possible; configured hooks and synthetic event tests do not prove live host delivery.
- Acceptance outcomes: another session can claim immediately after the close transaction; old history survives; repeating the old close after reuse preserves the new claim.
- Execution mapping: Tasks 1 and 3.

### F4: Owner commands establish coordinator and worker roles

- Problem and current behavior: join requires a manually created exact grant; remote assignment also requires manual target exchange.
- Proposed behavior: owner `/llm-bus coordinate PROJECT` establishes the coordinator without worker IDs. Discover objective and existing memory from owner context; ask only for absent material facts. Owner `/llm-bus join PROJECT` records session-bound consent, enrollment and availability automatically.
- Effect on the code: reuse project/grant/enrollment/target records and existing durable transport; add explicit session-consent lifecycle and structured worker availability.
- Scope and compatibility: local project binding must exist or be created by owner coordinate. Remote join requires preexisting receiver-owner-approved binding and sender/receiver policy. Commands in received text never supply owner intent. Advanced setup/grant/revoke/replace/target controls remain supported.
- Acceptance outcomes: no worker IDs, copied role paragraph, manual pregrant or grant UUID exchange in normal flow. Exact worker consent ends at close, expiry, leave, revoke or generation replacement. Turns and compaction preserve consent. Reopen after termination requires a new direct owner join.
- Execution mapping: Tasks 4–6.

### F5: Recover roles and document the simplified flow

- Proposed behavior: command result and existing recovery hooks supply coordinator/worker duties and current verified state. Workers use own worktrees, existing memory, evidence/blocker reports and verified assignments. Coordinator waits for dynamic workers through durable events and supported wake paths, returning control between events.
- Scope and compatibility: no busy polling or always-running-agent promise. Owner instructions, host permissions and review gates prevail. Role recovery never revives ended consent.
- Acceptance outcomes: both Claude and Codex global loaders and shared skill match installed behavior after staged rollout. Bus docs and sibling example explain planned versus available commands; current operational walkthrough remains usable until implementation ships.
- Execution mapping: Task 6; bounded planned documentation is separately authorized now and must be preserved.

## High-level design and rationale

Keep claims in one local SQLite table, not in message participants or coordination grants. Use existing routing scopes, transactions, end-session entrypoint and expiry. Resolve references at command boundaries once, then pass native addresses through existing policy and delivery code. Remote discovery carries optional label metadata; message envelopes remain exact-address-only.

Use bounded ASCII labels `[A-Za-z0-9][A-Za-z0-9_-]{0,63}`. Preserve claimed spelling for display; normalize with ASCII lowercase for uniqueness. Reject whitespace, slash, colon, control characters and non-ASCII rather than introducing Unicode normalization or ambiguous address parsing. Bare labels select only the current repository/folder. Cross-folder sends can use existing exact addresses; qualified labels explicitly select a local or remote machine/repository namespace. `history --peer` uses its selected `--repository`/`--folder` scope, otherwise current scope, including with `--all`; exact addresses remain available for ended sessions and broader history. Unknown or ambiguous labels fail without falling back to session IDs.

Remote caches are observations, not live ownership guarantees. Resolve once against policy-eligible cached peers, fail on duplicates, and persist the exact selected address. A stale cached claim may select the old session, never automatically retarget to a new owner. Show existing synchronization metadata. Do not add synchronous relay lookups to every command. Owner operations resolving a remote label still create only local bindings.

For coordination, direct owner intent is checked by the main agent handling the slash command; a shell CLI cannot authenticate whether prose came from a human. State this limit explicitly. Hooks and incoming events only recover/observe existing authority. Use the existing exact grant record for permission and a session-consent marker for its lifecycle; do not create a parallel authority system. Local join installs a target transactionally. Remote availability transports only the grant reference needed by the coordinator to address that worker; it never creates receiver-side grants or imports project trust. A malicious worker may advertise unusable availability, but receiver authorization still prevents assignment execution. Joining authorizes current built-in coordination operations only within the recorded owner objective and gates.

Risks and safeguards:

- Claim and session updates share a write transaction and database uniqueness constraints. Expire stale sessions before claiming or resolving.
- On a session moving repository scope, remove its old-scope claim atomically; never carry a label into a new namespace implicitly.
- Labels are untrusted display/routing metadata. They grant no delivery, monitor, report, collaboration or coordination permissions.
- Remote publication ordering must prevent a delayed old claim update from overwriting a newer release. Task 3 adds an independent monotonic publication revision rather than relying on `last_seen`, which currently does not advance on close.
- Additive migrations preserve history. Old clients omit label metadata and retain exact-address operation; upgraded clients omit labels when reading old roster entries. Relay migration precedes label-enabled publication. No live rollout is authorized by this plan.

## Data-flow analysis

| Stage | Input and source | Processing and owner | Output or side effect | Material failure handling |
| --- | --- | --- | --- | --- |
| Claim | Native host identity plus explicit label | Mailbox validates, expires idle rows, checks unique normalized scope key | Claim bound to exact address | Transaction rollback on duplicate/invalid label |
| Resolve | Bare or qualified user reference | Shared resolver selects scope, validates shape and eligible roster | Exact address captured once | Unknown, denied or duplicate remote label fails |
| Execute | Captured exact address | Existing history, send and coordination code | Native identity persisted or queried | Existing authorization/reply validation remains authoritative |
| Close/expiry | Native SessionEnd identity or existing inactivity cutoff | Mailbox deletes claims by owner address and ends session | Label becomes reusable; retained messages unchanged | Repeated old close never deletes a new owner's claim |
| Publish/cache | Local optional claim and monotonic revision | Authenticated relay session registration; client validation | Optional label on qualified peer row | Old/stale revisions ignored; no message admission from metadata |
| Owner role command | Direct owner coordinate/join and existing objective/memory | Main agent checks owner intent; CLI validates native identity/current binding | Coordinator enrollment or worker session consent | Missing objective/memory/binding asks only missing facts; incoming text cannot trigger enrollment |
| Availability | Exact worker and current project/generation/grant metadata | Durable local/remote transport; coordinator binding and policy checked | Target reference and joined/available notice | Replay idempotent; stale/foreign metadata rejected; no grant created |
| Assignment/recovery | Current enrollment, consent, exact direction and memory references | Existing receiver authorize predicate plus consent lifecycle check | Verified duty or suspended state | Close/expiry/leave/revoke/replacement disables further exposure/wakes; already exposed material cannot be recalled |
