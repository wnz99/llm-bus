## Features and effects

`llm-bus upgrade`, run from a clean llm-bus checkout, replaces the machine's
installed `llm-bus` uv tool with a wheel built from the checkout's `HEAD`. It
verifies the new install. Only after verification succeeds does it delete the
older package folders and the old release artifacts. If anything fails, it
deletes nothing and the previous install stays active. It refuses to start when
it could not restore the previous install. Nothing else in the bus changes: no
mailbox, hook, policy, instruction or backup state is touched. The command does
not rerun `llm-bus install` and does not manage bridge processes; its output and
the README name those as next steps.

Example, from the checkout root:

```text
$ uv run llm-bus upgrade
{"package_id": "1a2b3c4d", "reinstalled": true,
 "wheel": "/Users/me/.local/share/llm-bus/packages/1a2b3c4d/llm_bus-0.1.0-py3-none-any.whl",
 "extras": ["collab"], "python": "3.12", "binary": "/Users/me/.local/bin/llm-bus",
 "removed_packages": ["fabcb404"], "removed_releases": [],
 "next_step": "Close Claude Code and Codex, run `llm-bus install`, then restart them; restart any running `llm-bus bridge`"}
```

### F1: Build and install from the checkout

- Problem and current behavior: no product command installs or upgrades the tool. README documents `uv tool install .` and `uv tool install --force '.[collab]'`; past releases used one-off scripts under `~/.local/state/llm-bus/` that built wheels into `~/.local/share/llm-bus/packages/<sha>/` and installed them with `uv tool install --force`.
- Proposed behavior: `llm-bus upgrade` finds the Git root of the current directory and confirms it is an llm-bus checkout (`pyproject.toml` `[project] name = "llm-bus"`). It refuses when the resolved checkout lies inside `packages/` or `releases/`, because the prune would delete the checkout itself (past rollouts created release worktrees under `releases/`). It refuses when tracked files have uncommitted changes. It reads the current uv receipt and refuses unless the previous install can be restored (F2). It exports `HEAD` with `git archive`, builds a wheel in a fresh temporary folder under `packages/`, moves it into `~/.local/share/llm-bus/packages/<id>/` where `<id>` is the first 8 hex characters of the `HEAD` commit, and runs `uv tool install --force --python <checkout .python-version> <wheel>[<extras>]`. Extras come from the current receipt, so an install with `collab` keeps `collab`.
- Same `HEAD` already active: when the receipt already points into `packages/<id>/`, the command builds and installs nothing. It verifies the current install, then prunes on success (`"reinstalled": false`). This guarantees the build never overwrites the wheel the rollback depends on.
- Effect on the code: one new module `src/llm_bus/cli/upgrade.py` beside `cli/installation.py`; one new subcommand in `src/llm_bus/cli/parser.py` and one dispatch branch in `src/llm_bus/cli/app.py`.
- Scope and compatibility: additive. Untracked files (for example `.vscode/`) neither block nor enter the wheel. The command does not rewrite hooks: `llm-bus install` edits host settings and requires both agents to be closed (`README.md:## Install and verify`), which a command run from an agent session cannot guarantee. The README already says to rerun `llm-bus install` after upgrading, because a new version can change hook kinds or migrations even when the entrypoint path is unchanged. The `next_step` output and the README "Upgrade" paragraph therefore say: close the agents, run `llm-bus install`, restart them, and restart any running `llm-bus bridge`. A first-ever install, a directory install (`uv tool install .`) or a change of extras needs a one-time manual wheel install (README "Upgrade" bootstrap).
- Acceptance outcomes: wheel built from `HEAD` content only; dirty tracked checkout refused before any build; checkout inside a prune root refused before any build; extras preserved; `next_step` names hook reinstall and bridge restart; installed receipt points at the new wheel; same-`HEAD` rerun neither builds nor installs.
- Execution mapping: Task 1.

### F2: Verify, roll back on failure, refuse when rollback is impossible

- Problem and current behavior: rollout scripts ran ad hoc checks (`llm-bus coordination --help`); nothing guards against a bad install.
- Proposed behavior:
  - Precondition, checked before any build: `shutil.rmtree.avoids_symlink_attacks` is true (otherwise the later prune would refuse after the install). Then: the receipt exists, parses, and its `llm-bus` requirement `path` is an existing `.whl` file. Otherwise the command exits 1 with nothing built, installed or deleted. The message says the previous install cannot be restored on failure and points to the README bootstrap. This covers a missing receipt, a malformed receipt, a directory install and a deleted wheel.
  - Verification requires all of: (a) the receipt's `llm-bus` requirement path equals the expected wheel and its extras equal the requested extras; (b) the receipt's `llm-bus` entrypoint, run with `PATH=/usr/bin:/bin`, exits 0 for `upgrade --help` and prints `usage:`; (c) with `collab`, the tool environment's Python imports `llm_bus.collab.transport` (which imports `iroh`) under `-I`.
  - On install or verification failure after a reinstall, the command reinstalls the previous wheel with its recorded extras and recorded Python. It deletes nothing and exits 1 with a message naming the failure and the rollback outcome.
  - On verification failure in the same-`HEAD` case, nothing was installed, so the previous install is already the active one. The command deletes nothing and exits 1.
- Effect on the code: `src/llm_bus/cli/upgrade.py`.
- Scope and compatibility: the new `packages/<id>/` folder is kept on failure ("delete nothing"); the next successful upgrade prunes it. A later run on the same commit, while that folder is not active, overwrites its wheel with an identical-source build; it is never the rollback target, because the rollback target is the receipt's wheel in another folder.
- Acceptance outcomes: failed verification leaves every `packages/*` and `releases/*` entry in place, restores the previous wheel install, and returns exit code 1; a non-wheel previous install is refused before any build or install.
- Execution mapping: Task 1.

### F3: Prune old packages and release artifacts safely

- Problem and current behavior: old package folders and release artifacts accumulated until removed by hand on 2026-11-10.
- Proposed behavior: after verification succeeds, delete every entry in `~/.local/share/llm-bus/packages/` except the active `<id>`, and every entry in `~/.local/state/llm-bus/releases/`. Deletion is confined to those two directories: a root that is a symlink or not a directory is refused; symlinked entries are unlinked, never followed; directories are removed with `shutil.rmtree` only where it resists symlink attacks. `backups/`, `deploy-backups/` and all other state are never opened. When any release entry was removed, run `git worktree prune` in the checkout.
- Effect on the code: `prune_entries` in `src/llm_bus/cli/upgrade.py`.
- Scope and compatibility: keep none. Rollback means rebuilding from Git. A prune failure after successful verification leaves the new install active and exits 1, listing what was removed. Leftover `.upgrade-*` build folders from a killed run sit in `packages/` and are removed by the next successful prune.
- Acceptance outcomes: after success, `packages/` holds only `<id>/`, `releases/` is empty, siblings and symlink targets are intact.
- Execution mapping: Task 1.

## High-level design and rationale

One module, `src/llm_bus/cli/upgrade.py`, next to the existing install and uninstall logic in `cli/installation.py`:

- `prune_entries` owns the only deletion logic. It takes a root and an optional name to keep and returns removed names. It knows nothing about uv or Git, so its path-safety rules are testable on a plain temporary directory.
- `upgrade` owns the sequence: locate checkout, check cleanliness, read previous receipt and require a restorable wheel, detect same-`HEAD`, build, install, verify, roll back or prune. It returns a result dict that `cli/app.py` serializes like `install`.

Design choices:

- Package id = first 8 hex characters of the `HEAD` commit. This matches the existing `packages/fabcb404` convention and the "rollback means rebuilding from Git" decision; a content hash would not map back to a commit. Building from `git archive HEAD` makes the id truthful even when untracked files exist (hatchling would otherwise include untracked files under `src/llm_bus`); refusing tracked modifications avoids silently installing something other than what the user edited.
- Rollback needs a wheel. `uv tool install --force` replaces the tool environment before verification can run, so restoring the previous install means reinstalling exactly what the receipt recorded. A directory requirement cannot be restored: the directory is usually this checkout, now at the new `HEAD`. So the command refuses before any change instead of replacing an unrestorable install. Rejected alternative: copying the uv tool environment and entrypoint as a backup; it writes outside the two owned roots and depends on uv's private layout.
- Same-`HEAD` handling. Building into `packages/<id>/` when that folder is already active would overwrite the rollback wheel. The command therefore detects an active `<id>` before building and only verifies and prunes. Builds always land first in a fresh `packages/.upgrade-*` temporary folder, then move into `packages/<id>/` with `os.replace` (same filesystem).
- Extras preserved from the receipt, as the rollout script did (`install-b7b8117.py` read `"collab"` from the receipt). No `--extra` flag: changing extras is a one-time manual install.
- Python pinned to the checkout's `.python-version` (`3.12`). The current receipt records Python 3.14.8 although the wheel declares `Requires-Python: <3.13,>=3.12`; pinning to the CI and development interpreter removes that drift. The first upgrade therefore moves this machine's tool environment from 3.14 to 3.12. Rollback uses the receipt's recorded `python`, so it restores the previous interpreter too.
- Verification runs `upgrade --help` rather than plain `--help`: it imports the full CLI. The static version `0.1.0` cannot prove new code, so the receipt-path check carries that proof.
- Documented invocation is `uv run llm-bus upgrade` from the checkout. The installed binary predates the command on first use, and running from the project environment avoids replacing the running tool's own environment mid-process. `llm-bus upgrade` from the installed tool also works: every module it uses after install is imported at module load.
- Rejected: a cross-process lock. Concurrent upgrades are unlikely and their worst case is a receipt whose wheel was pruned by the other run; the installed environment still works and the next run refuses until a bootstrap reinstall. A POSIX `fcntl` lock would also break CLI import on Windows, which `mailbox.connection.default_path` still supports.
- Rejected: running `llm-bus install` or touching instruction blocks from the command. `install` edits host settings and requires both agents to be closed (`README.md:## Install and verify`); the command typically runs from an agent session. DISCOVERY places hooks out of scope unless needed. The hook reinstall stays a documented manual next step, consistent with the existing README instruction to rerun `llm-bus install` after upgrading.
- Rejected: stopping or restarting bridge processes from the command. Bridge supervision is machine-specific (this machine uses the LaunchAgent `sh.wnz.llm-bus-bridge` with `KeepAlive`); the command adds no launchd or service logic. `next_step` and the README name the restart.

Risks and safeguards:

- Deletion scope is the main risk. Safeguards: two fixed roots derived from the home directory; root `lstat` must be a real directory; entries enumerated with `os.scandir` and removed by name; symlink entries unlinked; `shutil.rmtree.avoids_symlink_attacks` required, else refuse; active `<id>` matches `^[0-9a-f]{8}$` (asserted when derived from `HEAD`), and `_verify` has already confirmed the receipt points at `packages/<id>/`.
- Release entries may be Git worktrees of this checkout. When any release entry was removed, run `git -C <checkout> worktree prune`. It only drops records whose directories are gone and skips locked worktrees.
- Machines installed the README directory way must bootstrap once before the command works. The refusal message and README say how.
- Deleting the running checkout: a checkout inside `packages/` or `releases/` is refused before any build.
- Running sessions and running `llm-bus bridge` processes keep the old code until restarted. The upgrade replaces the tool environment under a running bridge (the first upgrade also moves it from Python 3.14 to 3.12, so its `site-packages` path changes); a supervised bridge may crash and restart under the new code without an operator check. `docs/remote-bus.md:## Migration and rollback` already says to stop remote bridges before changing clients. Safeguard: the README says to stop the bridge before upgrading or restart it afterwards and check its log, and `next_step` says to restart it; final acceptance on this machine includes an owner-approved bridge restart and log check. Older binaries need not work against a newer store (DISCOVERY).
- Stale hooks: a new version can change hook kinds or migrations. Safeguard: `next_step` and the README direct `llm-bus install` with the agents closed.

## Design diagrams

```text
 llm-bus upgrade (cwd inside checkout)
        |
 [checkout root + name check] ----fail----> exit 1, nothing changed
        |
 [checkout inside prune root?] -----yes----> exit 1, nothing changed
        |
 [rmtree symlink-safe?] ------------no-----> exit 1, nothing changed
        |
 [tracked changes?] ---------------yes----> exit 1, nothing changed
        |
 [read receipt: wheel, extras, python]
        |
 [previous is existing .whl?] ------no----> exit 1, nothing changed
        |
 [receipt already in packages/<id>/?]
     |                         |
    yes                        no
     |                         |
     |      [git archive HEAD -> uv build in packages/.upgrade-*]
     |      [os.replace wheel -> packages/<id>/]
     |      [uv tool install --force --python X wheel[extras]]
     |                         |
 [verify receipt + binary + collab import]
     |                  |                      |
  pass               fail, reinstalled     fail, same HEAD
     |                  |                      |
     |       [reinstall previous wheel]   [nothing installed]
     |       [delete nothing] exit 1      [delete nothing] exit 1
     |
 [prune packages/* except <id>]
 [prune releases/*; if any removed: git worktree prune]

```

Every failure branch exits before `prune_entries`. `prune_entries` runs only after a passing verification.

`keep` is compared by exact name only; the caller validates it.

```python
PACKAGE_ID = re.compile(r"^[0-9a-f]{8}$")
VERIFY_PATH = "/usr/bin:/bin"
BOOTSTRAP = "install a wheel once as described in README 'Upgrade', then rerun"
RMTREE_UNSAFE = "Refusing to prune: platform rmtree follows symlinks"
NEXT_STEP = ("Close Claude Code and Codex, run `llm-bus install`, then restart them; "
             "restart any running `llm-bus bridge`")

@dataclass(frozen=True, slots=True)
class InstalledRequirement:
    path: Path                 # existing .whl file
    extras: tuple[str, ...]
    python: str | None         # receipt [tool].python, used only for rollback

def upgrade(start: Path, home: Path) -> dict[str, object]:
    uv = shutil.which("uv") or raise BusError("uv is required to upgrade llm-bus")
    checkout = _checkout_root(start)              # git rev-parse --show-toplevel; tomllib name == "llm-bus"
    packages = home / ".local/share/llm-bus/packages"
    releases = home / ".local/state/llm-bus/releases"
    for root in (packages, releases):             # compare resolved paths (macOS /var -> /private/var)
        if checkout.resolve().is_relative_to(root.resolve()):
```
