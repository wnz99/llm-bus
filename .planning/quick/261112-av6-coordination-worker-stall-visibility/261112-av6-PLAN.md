# Coordination work state Implementation Plan (r3)

Source: GitHub issue #76; owner decisions A and B and the later owner decisions
and simplicity dispositions in `DISCOVERY.md` ("Decisions and open questions",
2026-11-12). Out of scope: self-scheduled wakes and host activity time (option C).

Changes from r1: no per-turn coordinator message (P1); `directions` only in the
`show` handler (P2); `coordination direction-list PROJECT [--open]` with a fixed
cap of 100 (P3); `show` lists only directions that still need attention (P4);
`--stalled` replaced by `--open` with `state_changed_at` (P5); `reprioritize`
counts as work; `docs/machine-policy-plan.md` and the example rules file are
updated.

Changes from r2 (plan review C1R1 and its owner decisions): an acknowledged
later `cancel` direction to the same grant closes earlier work directions by
derivation, with no new report code (M1); `coordination_work_reports` uses
`CREATE TABLE IF NOT EXISTS` (L1); `transition_conflicts` returns `False`
without a prior report (L2); `reported_at` uses the `acknowledged_at` format
(L3); three more doc locations join Task 3 (L4); the owner-confirmed P4
adaptation is recorded (L5).

## Requirements and decisions

### Features and effects

Workers in a coordinated project can acknowledge a direction and then go idle
with queued work. The coordinator cannot tell this from busy work. This change
adds two things. First, guidance that makes workers start unblocked work before
they return control and record state changes without waking anyone. Second, a
recipient-recorded work state for each local direction that the coordinator can
read and list. The coordinator judges age; the bus does not claim to detect
stalls.

#### F1: Worker and coordinator duties (owner decision A, as amended)

- Problem and current behavior: `src/llm_bus/cli/guidance.py:_coordination_text`
  (role branch) says only "After handling events, return control." No rule tells
  a worker to start accepted, unblocked work or to record state. The same rule
  is copied in `skills/llm-bus/SKILL.md`,
  `skills/llm-bus/references/coordination.md` ("Durable work and ownership") and
  `examples/instructions/llm-bus-coordination.md`.
- Proposed behavior: the worker text says: before returning control, start every
  accepted direction that is no longer blocked; when a direction's state
  changes, record it with `llm-bus report ID --status STATUS` (wakes nobody);
  message the coordinator only for blockers and outcomes it must act on or
  learn, with evidence, never for presence or routine progress; a cancelled
  direction needs no report. This replaces
  the existing clause `report evidence and blockers to the coordinator`. The
  coordinator text says: check `llm-bus coordination direction-list PROJECT
  --open`, judge each open direction's age from `state_changed_at`, and follow
  up with a `clarify` direction when one looks stalled. "Return control" and
  "Never busy-poll" stay.
- Effect on the code: guidance string only; skill, tutorial and example rules
  copies match.
- Scope and compatibility: no behavior change. Hook guidance grows by about
  300 characters on every prompt (compact form also carries the role text).
  No per-turn or presence message exists.
- Acceptance outcomes: AC1.
- Execution mapping: Task 3.

#### F2: Remedy hint for the wake-turn decision refusal (owner decision A)

- Problem and current behavior: `decisions.WAKE_TURN` says only
  `Decision answers must come from an owner turn, not a bus wake`. The owner who
  answered in a question dialog inside a wake-started turn gets no next step.
- Proposed behavior: the refusal stays. The text keeps that first sentence and
  appends: `Ask the owner to type the answer as a new prompt in this session,
  then record it in that turn; an answer given inside a wake-started turn does
  not count`.
- Effect on the code: one constant; docs quoting it.
- Acceptance outcomes: AC2.
- Execution mapping: Task 3.

#### F3: Recipient-recorded work state for local directions (owner decision B)

- Problem and current behavior: `llm-bus report ID` accepts only imported
  (relay) messages (`src/llm_bus/reports/submissions.py:imported` raises
  `Report requires an imported message for this native recipient`).
  `status ID` fills `work_report` only for outgoing relay messages
  (`src/llm_bus/diagnostics/messages.py:_message_status`). A local direction has
  no work state.
- Proposed behavior: the same command records state for a local coordination
  direction the caller received and acknowledged (owner: acknowledgement is
  required before any state report):

  ```sh
  llm-bus --format agent report 42 --status received
  llm-bus --format agent report 42 --status proceeding --reason started
  llm-bus --format agent report 42 --status not_proceeding --reason dependency_blocked
  llm-bus --format agent report 42 --status completed
  ```

  The vocabulary is the existing built-in one (`REPORT_REASONS`). Owner terms map
  as: accepted = `received`; started = `proceeding/started` (or `resumed`);
  blocked = `not_proceeding/<reason>`; done = `completed`; plus `failed/<reason>`.
  `status 42` then shows
  `"work_report": {"message_id": 42, "revision": 2, "status": "proceeding", "reason": "started", "reported_at": "..."}`.
  Imported messages keep the relay path unchanged.
- Effect on the code: new module `src/llm_bus/coordination/work_state.py` owns the
  table, recording, snapshot and listing. `cli/commands.py` dispatches `report`
  by message origin. `reports/lifecycle.py` gains one shared transition rule.
  Schema 15 adds one table.
- Scope and compatibility: additive table; `status` field set unchanged;
  `work_report` for ordinary local and imported messages stays `null`.
- Acceptance outcomes: AC3, AC4, AC5, AC7.
- Execution mapping: Task 1.

#### F4: Direction state in `coordination show` and `direction-list` (owner decision B, P2–P5)

- Problem and current behavior: `coordination show` (`coordination/cli.py:_show`
  calls `store.show`) lists grants, enrollments and gate data, but no
  directions.
- Proposed behavior:
  - Item shape (both commands):
    `{"message_id", "recipient", "operation", "sent_at", "acknowledged_at", "remote_id", "work_report", "state_changed_at"}`.
    `state_changed_at` is the local report's `reported_at`; without a report it
    is `acknowledged_at`; it is `null` for an unacknowledged direction and for
    an outgoing relay direction that has a relay report (the relay stores no
    report time locally).
  - Visibility: the enrolled coordinator sees directions it sent; any other
    viewer sees only directions addressed to itself. Current project
    generation only. Newest first. At most 100 items (`MAX_DIRECTIONS`), counted
    after filtering.
  - Cancelled work direction (owner decision C1R1 M1): a direction with
    operation `assign`, `review` or `reprioritize` for which the listed rows
    contain a `cancel` direction with all of: a greater local message ID
    (`messages.id`, "later"), an equal `grant_id`, `project_id` and
    `generation` in `coordination_messages.metadata_json`, the same `sender`
    and `recipient`, and `acknowledged_at` set. The state is derived at read
    time; nothing is written. A work direction sent after the cancel stays
    open. A `cancel` closes only work directions, never another `cancel`,
    `clarify`, `pause` or gate approval.
  - Open direction: acknowledged, operation `assign`, `review` or
    `reprioritize`, not an imported message, no `completed` or `failed`
    report, and not cancelled.
  - `coordination show PROJECT` adds `directions`: directions that still need
    attention, meaning unacknowledged directions of any operation, except
    cancelled work directions, plus open directions. Present only when
    non-empty. Only the `show` action adds it;
    other coordination actions that return `store.show` are unchanged.
  - New `coordination direction-list PROJECT [--open]` returns
    `{"directions": [...]}`: all directions without a flag (cancelled work
    directions included, item shape unchanged), open directions with
    `--open`. No `--limit`.
- Effect on the code: `work_state.listing`; `coordination/cli.py` (`_show`,
  new `_direction_list`, parser, `ACTIONS`). `store.show` is not changed.
- Scope and compatibility: outgoing relay directions use the relay snapshot, as
  `status` does. That snapshot exists only when both owners allow reports
  (`send_reports` / `receive_reports`); otherwise it is `null` and the direction
  stays open. On the worker's machine, imported directions show
  `work_report: null` (their report state lives in the relay submission queue)
  and are never open there. An outgoing relay `cancel` closes earlier work
  directions once its sender copy has `acknowledged_at`, which the relay sets
  when the worker acknowledges (`remote/outbox.py`). Cancellation uses no
  report, so it works even when reports are not allowed between the owners.
- Acceptance outcomes: AC6, AC7.
- Execution mapping: Task 2.

### High-level design and rationale

- Reuse the report protocol, not a new vocabulary. `REPORT_REASONS`,
  `validate_status`, `TERMINAL` and the "no return to `received`, nothing after
  a terminal status" rule already express accepted/started/blocked/done/failed
  with fixed reasons. One command (`report`) serves local and remote directions.
- Do not reuse the relay tables. `remote_reports` and
  `remote_report_submissions` are keyed by relay UUID and model relay revisions,
  deadlines, sync and peer policy. A small local table `coordination_work_reports`
  keyed by the local message ID avoids distorting them.
- Authorization: only the native session whose address equals
  `messages.recipient` may record state, after it acknowledged the message, and
  only for a message with a `coordination_messages` row and no
  `remote_imports`/`remote_outbox` row. Unknown and not-own messages raise the
  same error, so the command cannot probe other sessions' directions.
  `require_main_agent` in `cli/app.py:main` already refuses sub-agents.
- Prompt and wake isolation (AGENTS.md): recording writes only
  `coordination_work_reports`. It inserts no message, calls no
  `request_dispatch`/`dispatch_pending`, and changes no hook guidance. State is
  read only by agent-invoked commands (`status`, `coordination show`,
  `coordination direction-list`), as relay `work_report` already is through
  `status` and `remote-status`. Values are fixed codes and timestamps; no free
  text exists to inject.
- Communication efficiency (owner decision 2026-11-12, P1): state changes go
  through the fixed-code `report` only. Bus messages to the coordinator carry
  only blockers and outcomes it must act on or learn. No per-turn, presence or
  routine-progress message.
- Open is a fact, not a stall verdict (P5). `--open` lists acknowledged work
  directions without a terminal report and gives `state_changed_at`. The
  coordinator judges age. No threshold setting is added; the bus cannot see host
  activity.
- `directions` only in the `show` handler (P2). `store.show` is the default
  result of every coordination action without its own result
  (`coordination/cli.py:run`) and of setup. Adding the list there would put it
  in every mutation output.
- P4 adaptation, owner-confirmed (DISCOVERY C1R1 L5, 2026-11-12): `clarify`,
  `pause`, `cancel` and gate approvals carry no work, so workers never report
  them terminal. A literal non-terminal filter would keep every such direction
  in `show` until the cap fills. `show` therefore lists unacknowledged
  directions of any operation plus open work directions. This keeps the intent
  of P4 (no settled history in `show`).
- Cancelled directions close by derivation (owner decision C1R1 M1). A
  `cancel` direction names a grant, not a message (`coordination/models.py:
  Direction` has `project_id`, `generation`, `grant_id`, `operation` and no
  target message ID), and `skills/llm-bus/references/coordination.md:535`
  says `Cancellation means stop and report state`. The grant belongs to one recipient in one
  generation (`coordination_targets` key `scope, project_id, recipient`). So an
  acknowledged later `cancel` with the same grant, generation, sender and
  recipient closes every earlier work direction. No report code is added and the
  relay report protocol is unchanged. Workers need not report on cancelled
  directions. The derivation uses rows the listing already reads, so it adds no
  query.

Risks and safeguards:

- Schema 15: an older client opening the mailbox fails with `Mailbox schema is
  newer than this llm-bus version` (existing `_version` behavior). Rollback is
  in "Verification and rollback".
- Self-reported state: the bus cannot verify that work runs. A worker that
  reported `proceeding` and stopped looks the same as one still working; only
  `state_changed_at` age shows it. Docs state this under Known limits.
- Cancellation is grant-wide: one acknowledged `cancel` closes every earlier
  open work direction to that worker, including ones the coordinator meant to
  keep. The coordinator resends any direction that should continue; a direction
  sent after the cancel stays open. Unacknowledged `cancel` closes nothing, so
  the worker's acknowledgement stays the trigger. `messages.id` is `INTEGER
  PRIMARY KEY` without `AUTOINCREMENT`; a later insert still gets an ID above
  every retained row, so "later" holds while the earlier direction exists.
- A worker that ignores a cancel and later reports `completed` on the earlier
  direction is still allowed; the direction stays closed either way.
- A direction superseded without a `cancel` (for example a newer `assign` to the
  same worker) stays open until the worker reports `completed` or `failed`, as
  in r2.
- Cap: more than 100 matching directions in one generation drops the oldest.
  The filter runs before the cap, so `--open` loses items only past 100 open
  directions.
- Listing reads every direction row of the current generation for the viewer
  before filtering (relay snapshots are parsed in Python). Acceptable for local
  SQLite at expected volumes; no index is added.
- Hook guidance length grows; `tests/local/test_hook_guidance.py` keeps the
  compact/full length relation.

**Intended edits:**

- `reports/lifecycle.py`:

  ```python
  def transition_conflicts(prior_status: str | None, status: str) -> bool:
      """A changed report may not follow a terminal one or return to received."""
      if prior_status is None:
          return False
      return prior_status in TERMINAL or status == "received"
  ```

  The helper owns the "no prior report" case (C1R1 L2): the first report of any
  valid status, including `received`, never conflicts. This makes the declared
  `None` argument safe instead of relying on every caller to guard it; a
  missing guard would otherwise refuse every first `received` report.
  `submissions.enqueue` uses
  `if transition_conflicts(prior["status"] if prior else None, selected)`, which
  keeps its current behavior (`prior and ...` was the only `None` guard).
  `work_state.record` passes the prior local status or `None` the same way.
- `coordination/work_state.py` (imports only `errors`, `reports.protocol`,
  `reports.lifecycle`; never `coordination.store`, to avoid a cycle):

  ```python
  WORK_OPERATIONS = ("assign", "review", "reprioritize")
  NOT_RECIPIENT = "Report requires a received local coordination direction or an imported message"
  UNACKNOWLEDGED = "Acknowledge the direction before reporting its state"

  def create_tables(db: Connection) -> None
      # CREATE TABLE IF NOT EXISTS coordination_work_reports(
      # message_id INTEGER PRIMARY KEY REFERENCES messages(id),
      # revision INTEGER NOT NULL CHECK(revision>0), status TEXT NOT NULL,
      # reason TEXT, reported_at TEXT NOT NULL)
  def imported(db: Connection, message_id: int) -> bool  # remote_imports.local_id
  def record(db: Connection, message_id: int, recipient: str,
             status: object, reason: object) -> dict[str, object]
  def snapshot(db: Connection, message_id: int) -> dict[str, object] | None
  def work_report(db: Connection, tables: set[str], message_id: int, *,
                  remote_id: str | None, imported: bool) -> object
  ```

  `record` (caller already ran `BEGIN IMMEDIATE`): `validate_status` first;
  select `m.recipient, m.acknowledged_at` from `coordination_messages c JOIN
  messages m` where no `remote_imports`/`remote_outbox` row exists; missing row
  or `recipient != caller` raises `NOT_RECIPIENT`; `acknowledged_at IS NULL`
  raises `UNACKNOWLEDGED`; identical prior `(status, reason)` returns the prior
  snapshot unchanged; `transition_conflicts` raises `TRANSITION_CONFLICT`;
  revision = prior + 1 (or 1), refuse above `MAX_REVISION`; upsert with
  `reported_at = strftime('%Y-%m-%dT%H:%M:%fZ','now')` in SQL, the same
  expression and clock that set `acknowledged_at` (`mailbox/writes.py:216`), so
  `state_changed_at` has one millisecond `Z` format for report and ack times
  (C1R1 L3; `record` therefore takes no `now` argument). `create_tables` uses
  `CREATE TABLE IF NOT EXISTS`, the pattern of `coordination/store.py`
  `create_tables`, because existing upgrade tests reset `user_version` without
  dropping tables and the documented rollback leaves the table (C1R1 L1).
  `snapshot` re-validates with `validate_status`
  and returns `{"message_id", "revision", "status", "reason", "reported_at"}`.
  `work_report`: outgoing relay (`remote_id` set) parses `remote_reports` with
  `parse_report` exactly as `_work_report` did (only if the table exists);
  `imported` gives `None`; otherwise `snapshot` if `coordination_work_reports`
  exists, else `None`.
- `mailbox/schema.py`: `SCHEMA_VERSION = 15`, `WORK_STATE_SCHEMA_VERSION = 15`;
  in `ensure_schema` after the host-process step:
  `if version < WORK_STATE_SCHEMA_VERSION: work_state.create_tables(db)`.
- `diagnostics/messages.py`: `"work_report": work_state.work_report(db, tables,

Rollback:

- Code: revert the merge commit. Ordinary messages and relay reports are
  unaffected by the revert.
- Data: a mailbox already at schema 15 is refused by an older client
  (`Mailbox schema is newer than this llm-bus version`). The new table is
  additive. To downgrade: stop all sessions and the bridge, back up the mailbox
  file, run `sqlite3 "$LLM_BUS_DB" 'PRAGMA user_version=14'`, then reinstall the
  older version. The older version ignores the leftover
  `coordination_work_reports` table. A later upgrade reuses it with its rows,
  because `create_tables` uses `CREATE TABLE IF NOT EXISTS`
  (`test_reupgrade_after_rollback`). Cancel-derived closure stores nothing, so
  it needs no data rollback.
